# N103 Gemini Chat Assignment 1

Android Studio implementation of the Mobile Application Development assignment, based on [ifahimkhan/GeminiApiComposeStarter](https://github.com/ifahimkhan/GeminiApiComposeStarter).

Roll number: **N103**  
Submission branch: **N103-assignment-1**

## Open and run

1. Open this root folder in Android Studio, where `settings.gradle.kts` is located. Do not open the nested `GeminiApiComposeStarter` backup folder.
2. Use Android Studio's bundled JDK and allow Gradle sync to finish. Install Android SDK Platform 36 when prompted. The app supports Android 8.0 / API 26 and later.
3. Copy `local.properties.example` to `local.properties` only if that file does not already exist. Preserve the `sdk.dir` line generated by Android Studio.
4. Obtain a Gemini API key in Google AI Studio and add `GEMINI_API_KEY=your_key_here` to `local.properties`. Never put a real key in tracked source, screenshots, issues, or a PR. CI can supply the `GEMINI_API_KEY` environment variable instead; a nonempty local value takes precedence.
5. Select a phone emulator or connected device and run the `app` configuration.
6. Enter a prompt, tap Send, and wait for the reply. The microphone button launches the device's speech recognizer; devices without a recognizer show an error with typing still available.

The starter SDK is retained to match the assignment's `GenerativeModel` requirement. It uses `gemini-3.6-flash`, configurable in `GeminiRepositoryImpl`. Google no longer actively maintains the legacy Android Gemini SDK. Model availability, key permissions and quota depend on the Google project; confirm these in AI Studio if requests fail. For future production work, migrate to a supported integration such as Firebase AI Logic or a backend.

## Implemented features

- Material 3 chat bubbles with stable Room message IDs, a `LazyColumn` and automatic scrolling.
- ViewModel-owned `ChatUiState`, exposed as read-only `StateFlow`, with lifecycle-aware collection in `ChatRoute`. `ChatScreen` takes state and callbacks; only transient scrolling and activity-launcher state remain in Compose.
- Window size classes, constrained content width on tablets, responsive bubble widths and keyboard insets.
- Progress display, duplicate-send prevention, bounded network requests, safe error messages, editable prompt restoration and error dismissal.
- Voice-to-text through `RecognizerIntent` and `rememberLauncherForActivityResult`.
- Room history that survives app restarts; clear-chat action disabled while a request is running.
- A compact-bubble preference persisted in Preferences DataStore.
- System dark theme and dynamic Material 3 colors on Android 12 and later.
- Android Keystore AES-256-GCM encryption of the API key at rest, with encrypted values in DataStore.
- Release minification with R8.

Each API call currently sends the current prompt. Saved messages are displayed as local history; they are not automatically sent as model context.

## Security flow and limits

Gradle reads `GEMINI_API_KEY` from the ignored `local.properties`, or the environment fallback, into `BuildConfig`. During startup, an IO coroutine initializes `ApiKeyVault`. Android Keystore generates a non-exportable 256-bit AES key with GCM and no padding. Each initialization uses a fresh random IV, and DataStore saves only the ciphertext (including its authentication tag) and IV. Initialization also refreshes the ciphertext when a new build supplies a rotated API key.

Immediately before constructing `GenerativeModel`, the repository retrieves the decrypted key in memory. It does not retain a separate plaintext key property. Initialization and decryption are serialized with a mutex. No raw SDK exception or key is logged, displayed or included in error UI. The SDK necessarily receives the plaintext key in memory to authenticate requests.

Backups and device transfer of application files, databases and preferences are excluded because the Keystore key is bound to the original installation/device. Chat history remains private local app data. Uninstalling the app removes its history and preferences.

**This is an assignment implementation, not a way to conceal a distributed API key.** `BuildConfig` embeds the key into the app, so an attacker can recover it from the APK or runtime despite encryption and R8. The production design should keep credentials on a backend proxy that authenticates users and enforces quotas, or use Firebase AI Logic with App Check and appropriately restricted keys. Do not publish an APK containing your personal unrestricted key.

## Tests

From Android Studio's Terminal, run:

```bash
./gradlew testDebugUnitTest
./gradlew connectedDebugAndroidTest
./gradlew assembleDebug assembleRelease
```

The connected tests require a running emulator or device. Unit tests use a fake `GeminiRepository` and `kotlinx-coroutines-test`; they need no network or live API key. Compose tests also use supplied UI state and callbacks, not live Gemini requests.

- ViewModel: success, progress state, duplicate sends, preserving a newly typed draft, failure with safe error text, blank-input rejection, restored history/preferences, clearing history and cancellation.
- Compose: entering text and sending, disabled Send while loading, visible progress/errors, dismissal, voice callback, expanded layout and preference callback.
- Device persistence: close and reopen a Room database, recreate the preference repository, decrypt across vault recreation, rotate synthetic keys, and check that DataStore does not contain their plaintext.

Reports are generated in `app/build/reports/tests/` and `app/build/reports/androidTests/`. See `docs/VALIDATION.md` for actual results and remaining manual checks.

## Performance review

Network and key operations run on `Dispatchers.IO`; Room suspending queries and DataStore manage their own background IO. Message IDs are stable keys, scrolling reacts to message IDs/loading changes, and duplicate requests are blocked while busy.

For the assignment's manual profiling step, run the debug app, open Android Studio's Layout Inspector and enable recomposition counts. Type a draft and toggle compact bubbles while inspecting which nodes recompose. Repeat with a long conversation and record the observation in the PR. Automated tests do not measure real-device latency or recomposition counts.
